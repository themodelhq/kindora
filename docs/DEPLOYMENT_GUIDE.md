# KINDORA v1.0.1 — Deployment Guide (Netlify + Render)

This guide deploys the hardened v1.0.1 stack. Architecture is unchanged from v1.0.0: **frontend** on Netlify (React/Vite PWA), **API** on Render Web Service, **PostgreSQL** Render DB, **Redis** Render Key Value, **workers** Render Background Worker, **cron jobs** Render Cron, **files** external S3-compatible object storage.

> Honest note: this document describes a deployment that has NOT been executed — no cloud accounts or real provider credentials were available in the build environment. All commands/configuration have been locally validated (YAML parse, `prisma migrate deploy` against a real PostgreSQL 18.6, production fail-fast boot probes). §9 lists the first-deploy verification checklist.

---

## 1. Prerequisites

1. GitHub repository containing this source.
2. Render account (Blueprint-capable) + Netlify account.
3. An S3-compatible bucket (Render Object Storage, Cloudflare R2, Backblaze B2, MinIO) with **private** ACL defaults.
4. SMTP credentials (transactional email).
5. At least one payment provider account: Paystack (recommended for recurring), Flutterwave, Stripe, PayPal.
6. A domain (optional at first: Netlify `*.netlify.app` + Render `*.onrender.com` work pre-DNS).

## 2. Database (Render Blueprint does this for you)

Deploy via Render **Blueprint** (`render.yaml` at repo root). It creates: `kindora-api` (web, standard), `kindora-worker` (standard), `kindora-redis` (keyvalue, noeviction), 6 cron jobs, `kindora-db` (postgres, basic-256mb; consider `standard` for high volume). All services are region-pinned to `oregon`.

Migrations run automatically on every API deploy through `preDeployCommand: npx prisma migrate deploy` — **forward-only**, never destructive; a failed migration aborts the release. NEVER run `prisma migrate reset` or `db push` against production.

## 3. Environment variables (complete reference)

`sync: false` values are prompted securely in the Render dashboard at first deploy. Full doc: `docs/ENVIRONMENT_VARIABLES.md`; template: `backend/.env.example`.

**API (`kindora-api`)**
| Variable | Value / source | Notes |
|---|---|---|
| NODE_ENV | `production` | enables fail-fast validation |

| PROVIDER_MODE | `live` | `mock` is REFUSED in production |
| JWT_ACCESS_TTL / JWT_REFRESH_TTL_DAYS | `900` / `30` | |

| STORAGE_ENDPOINT / BUCKET / REGION / ACCESS_KEY / SECRET_KEY / FORCE_PATH_STYLE / PUBLIC_BASE_URL / MAX_UPLOAD_MB | operator | MAX_UPLOAD_MB is enforced at the storage boundary via POST policy |
| SMTP_* / EMAIL_FROM_ADDRESS / EMAIL_FROM_NAME | operator | |
| PAYSTACK_SECRET_KEY / FLUTTERWAVE_SECRET_KEY / FLUTTERWAVE_WEBHOOK_HASH / STRIPE_SECRET_KEY / STRIPE_WEBHOOK_SECRET / PAYPAL_CLIENT_ID / PAYPAL_CLIENT_SECRET / PAYPAL_WEBHOOK_ID / PAYPAL_ENV | operator | at least ONE provider required or startup refuses |

**Frontend (Netlify build env):** `VITE_API_URL` (e.g. `https://kindora-api.onrender.com`), optionally `VITE_DEMO_MODE` (NEVER set in production builds).

## 4. Provider webhooks to configure

| Provider | URL to register | Notes |
|---|---|---|
| Paystack | `https://<api-domain>/api/v1/payments/paystack/webhook` | at minimum `charge.success`, `charge.failed`, `refund.processed`, `charge.dispute.*` |
| Flutterwave | `.../payments/flutterwave/webhook` | set the secret hash in `FLUTTERWAVE_WEBHOOK_HASH` |
| Stripe | `.../payments/stripe/webhook` | `checkout.session.completed`, `checkout.session.async_payment_*`, `checkout.session.expired`, `charge.refunded`, `charge.dispute.*` |
| PayPal | `.../payments/paypal/webhook` | `PAYMENT.CAPTURE.COMPLETED/REFUNDED/REVERSED/DENIED`, `CUSTOMER.DISPUTE.*` |

All four verify signatures over the raw body and then re-verify the transaction against the provider API — misconfigurations surface as `WebhookEvent` rows with `handledAction`, visible in the Financial Centre.

## 5. Production administrator bootstrap

The seed refuses to run against production. Create the first admin ONCE:

```
# in the Render shell for kindora-api (or any client with the DB URL):
NODE_ENV=production DATABASE_URL=... ADMIN_EMAIL=admin@yourdomain.org \
  ADMIN_PASSWORD='<generated: >=12 chars, upper+lower+digit+symbol>' \
  ADMIN_FIRST_NAME=... ADMIN_LAST_NAME=... npm run bootstrap:admin
```

It refuses when any admin exists, refuses weak passwords, never logs the password, and writes an `ADMIN_BOOTSTRAP` audit record. **Change the password after first login** (privileged-account MFA/2FA is on the roadmap; see SECURITY_AUDIT.md residual risks).

## 6. Netlify

`frontend/netlify.toml` is preconfigured: SPA fallback, security headers (CSP incl. `https://*.onrender.com` connect-src for pre-DNS deploys, HSTS), `no-cache` for `sw.js`/`index.html`, immutable assets. Set `VITE_API_URL` in Site settings → Build & deploy → Environment. The service worker never caches `/api/`.

## 7. First-deploy sequence

1. Render → New → Blueprint → select repo → fill the `sync: false` prompts → Apply.
2. Wait for `kindora-api` to become live (its preDeploy runs migrations).
3. Create the admin (§5).
4. Configure provider dashboards (webhooks §4 + return/redirect URLs if applicable).
5. Deploy frontend on Netlify with `VITE_API_URL`; then set `CORS_ORIGINS` on Render to the exact Netlify origin and redeploy the API.
6. Register uptime monitors for `/api/v1/health` AND `/api/v1/health/database` (a 200 on liveness alone does not prove DB reachability).

## 8. Cron jobs created by the blueprint

| Job | Schedule | Purpose |
|---|---|---|
| daily-analytics | 02:30 | StatDaily rollups |
| campaign-reminders | hourly | ending-soon campaigns |
| **recurring-donations** | every 15 min | **real off-session charges (Paystack)**, retries, failure notifications |
| weekly-reports | Mon 07:00 | organizer/owner digests |
| database-maintenance | Sun 03:00 | cleanup/expiry |
| reconciliation-digest | daily 04:00 | stale-PENDING/reconciliation email to admins |

## 9. First-deploy verification checklist (execute after you deploy)

1. `curl https://<api>/api/v1/health` → 200; `/api/v1/health/database` → 200.
2. Register a user; reload the page → still signed in (session restore).
3. Sandbox-mode payment (e.g. Paystack test key) → donate → verify `PENDING → SUCCEEDED` → receipt; check the ledger feed `/api/v1/impact/transactions`.
4. Send a provider webhook replay twice → exactly one ledger posting (Financial Centre → Payments reconciliation shows `DUPLICATE` handling).
5. Request a small withdrawal → approve with admin A → second approval (if above threshold) → mark paid with a real reference → Financial Centre → Withdrawals shows the payout reconciled.
6. Upload a private document as user B, try to fetch it as user C → 403; as admin → 200 + audit row.
7. Trigger a recurring schedule (small amount) → confirm one charge, one donation row, one ledger posting.
8. Run `npm run prisma:migrate` status check (`prisma migrate status`) — no drift.
9. Re-run the CI pipeline on the deployed commit and confirm the security job passes.

## 10. Secrets & credential hygiene

- No real credentials are committed anywhere in this repository (verified).
- Render `generateValue: true` for JWT/SESSION secrets; everything else `sync: false`.
- Rotate the seeded/admin passwords immediately after first login; rotate provider keys on any suspicion; see RECOVERY_GUIDE.md §Secret rotation.
