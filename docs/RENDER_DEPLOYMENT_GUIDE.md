# KINDORA v1.0.4 — Render Deployment Guide

Source of truth: `render.yaml` at the repository root. This guide is the operator
procedure for deploying the full KINDORA stack (API, workers, cron jobs, PostgreSQL,
Redis-compatible Key Value) to Render using the blueprint.

## 1. What the blueprint creates

| Service | Type | Plan | Root dir | Purpose |
| --- | --- | --- | --- | --- |
| `kindora-api` | web (node) | standard | `backend` | NestJS API. Runs migrations. |
| `kindora-worker` | worker (node) | standard | `workers` | BullMQ background workers. |
| `kindora-redis` | keyvalue | starter | — | Redis 7 instance, `maxmemoryPolicy: noeviction`. |
| `kindora-db` | postgres | basic-256mb | — | PostgreSQL (`kindora` / `kindora`). |
| `kindora-daily-analytics` | cron | — | `workers` | `30 2 * * *` → `node dist/cron/daily-analytics.js` |
| `kindora-campaign-reminders` | cron | — | `workers` | `5 * * * *` → `node dist/cron/campaign-reminders.js` |
| `kindora-recurring-donations` | cron | — | `workers` | `*/15 * * * *` → `node dist/cron/recurring-donations.js` |
| `kindora-weekly-reports` | cron | — | `workers` | `0 7 * * 1` → `node dist/cron/weekly-reports.js` |
| `kindora-database-maintenance` | cron | — | `workers` | `0 3 * * 0` → `node dist/cron/db-maintenance.js` |
| `kindora-reconciliation-digest` | cron | — | `workers` | `0 4 * * *` → `node dist/cron/reconciliation-digest.js` |

Plan discipline: API and worker run on `standard` — financial operations need
consistent CPU/memory and must never sleep. Do not downgrade to `starter` for a live
fundraising deployment (starter is acceptable only for a pre-launch staging copy).

## 2. Blueprint deploy, step by step

1. Push the repository to the connected GitHub repo.
2. Render dashboard → **New → Blueprint** → select the repository. Render reads
   `render.yaml` and shows every service it will create.
3. For each `sync: false` env var, Render prompts you for the value at deploy time.
   Enter the secrets (section 3). Nothing secret is ever stored in the blueprint file.
4. Confirm creation. The API build command is `npm ci && npm run build` (rootDir
   `backend`), start command `npm run start:prod`, and `autoDeploy: true` on push.
5. After the first deploy, register the admin user (see
   `backend/prisma/bootstrap-admin.ts` / seed) before attempting any payout work.

## 3. Required `sync: false` secrets (prompted at deploy time)

You will be prompted for all of these. Values marked **required** must be non-empty.

**Frontend/URLs**
- `FRONTEND_URL` (required) — exact production frontend origin, e.g. `https://app.kindora.com`.
- `BACKEND_URL` (required) — public API origin, e.g. `https://api.kindora.com`.
- `CORS_ORIGINS` (required) — comma-separated list of the exact frontend origin(s).
  Cookie CSRF checks fail closed when empty. Must include the Netlify domain
  (see `docs/NETLIFY_DEPLOYMENT_GUIDE.md`).

**v1.0.4 payout-lockdown vars**
- `MFA_ENCRYPTION_KEY` (optional but recommended) — dedicated AES key material for
  TOTP secret encryption at rest. When unset, the key is scrypt-derived from
  `JWT_SECRET` with domain separation (`kindora-mfa-v1`). Set a dedicated key so that
  rotating `JWT_SECRET` does not orphan enrolled MFA credentials.

**Storage (S3-compatible)**
- `STORAGE_ENDPOINT`, `STORAGE_BUCKET`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY`,
  `STORAGE_PUBLIC_BASE_URL` (all required for document/payout-evidence uploads).
  Fixed by blueprint: `STORAGE_REGION=us-east-1`, `STORAGE_FORCE_PATH_STYLE=true`,
  `STORAGE_MAX_UPLOAD_MB=15`.

**SMTP**
- `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM_ADDRESS` (required —
  verification emails, reconciliation digest).

**Payment providers** (at least one is mandatory: `PROVIDER_MODE=live` with zero
provider keys refuses to boot)
- `PAYSTACK_SECRET_KEY` (required for NGN payouts/transfers)
- `FLUTTERWAVE_SECRET_KEY`, `FLUTTERWAVE_WEBHOOK_HASH`
- `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`
- `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID`
- `PAYPAL_ENV` — ships as `sync: false` on purpose: the operator MUST consciously
  choose `live` after PayPal production onboarding. There is no sandbox default.

**Push / AI / observability** (feature-gated, can be supplied later)
- `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`
- `AI_PROVIDER_API_KEY`, `AI_PROVIDER_BASE_URL`, `AI_PROVIDER_MODEL`
- `SENTRY_DSN`

Worker-only prompt: `ADMIN_EMAILS` (comma-separated; recipients of the reconciliation
digest and weekly reports) and optional `MALWARE_SCAN_ENDPOINT` (when empty, sensitive
documents stay quarantined — fail-safe — and public images are re-encoded).

Auto-generated by Render (`generateValue: true`, do not override casually):
`JWT_SECRET`, `SESSION_SECRET`.

## 4. How migrations run (preDeployCommand)

- The API service declares `preDeployCommand: npx prisma migrate deploy`.
- Migrations run **only** through the API service's pre-deploy step. Workers and cron
  jobs never run `prisma migrate` — there are no concurrent migration runs.
- Forward-only. A failed migration blocks the release from starting and Render rolls
  the deploy back (see `docs/DATABASE_MIGRATION_GUIDE.md`).
- The worker image embeds the same Prisma schema (`workers/prisma/schema.prisma`) so it
  can read new columns/tables only after the API's pre-deploy succeeded.

## 5. Health and readiness checks

| Endpoint | Meaning | Notes |
| --- | --- | --- |
| `GET /api/v1/health` | Liveness | Render `healthCheckPath`. Never touches external systems. |
| `GET /api/v1/health/database` | Readiness | `SELECT 1`; 503 when DB unreachable. |
| `GET /api/v1/health/redis` | Redis readiness | `PING`; returns `configured: true/false`. |

v1.0.4 rule: `/health/redis` is **mandatory-ready for payout operations**. MFA
challenges live only in Redis and fail closed — when Redis is down, `POST /mfa/challenge`
and every guarded payout endpoint return **503** and all settlement/approval work stops.
Point uptime monitors at `/api/v1/health` **and** `/api/v1/health/database`, and alert on
`/api/v1/health/redis` going degraded: a 200 on liveness alone does not prove the
database is reachable, and a healthy liveness does not prove payouts are possible.

## 6. Verifying the deploy (curl)

```bash
BASE=https://<your-api>.onrender.com

# 1. Liveness
curl -sS $BASE/api/v1/health
#    {"status":"ok","service":"kindora-api","version":"...","uptimeSeconds":...}

# 2. Database readiness
curl -sS -f $BASE/api/v1/health/database
#    {"status":"ok","component":"database"}

# 3. Redis readiness (must be ok before payout operations)
curl -sS -f $BASE/api/v1/health/redis
#    {"status":"ok","component":"redis","configured":true}

# 4. MFA policy introspection (ADMIN JWT required)
curl -sS -H "Authorization: Bearer $ADMIN_JWT" $BASE/api/v1/mfa/policy
```

If `/api/v1/health` returns 502/503 immediately after a deploy, check the API log for
`Refusing to start: production configuration is unsafe.` — the startup validator is
doing its job (see `docs/PRODUCTION_ENVIRONMENT_VARIABLES.md`).

## 7. API + workers share the same payout policy env

`render.yaml` wires `DATABASE_URL` and `REDIS_URL` from the same `kindora-db` /
`kindora-redis` resources into the API, the worker, and every cron job. There is
deliberately **no per-service override** of `WITHDRAWAL_DUAL_APPROVAL_MODE`: no service
may run a different dual-approval threshold than any other. If you ever add an env var
to one service, mirror the payout-policy vars (`WITHDRAWAL_DUAL_APPROVAL_MODE`,
`WITHDRAWAL_DUAL_APPROVAL_THRESHOLD_MINOR`, `PROVIDER_MODE`) exactly across API and
workers, and re-verify with:

```bash
# Worker/cron logs must show the same PROVIDER_MODE as the API (live).
# MOCK payouts are forbidden in production: POST /withdrawals/:id/settle with
# payoutProvider=MOCK returns 403 in prod (PayoutService.startAttempt).
```

## 8. Rollback notes

- **Bad code release:** Render → service → **Events** → *Rollback* to the previous
  deploy. `preDeployCommand` re-runs the previous image's migration set — because
  migrations are additive and forward-only, re-running them is a no-op.
- **Failed migration:** the release never starts; Render keeps the previous deploy
  live. Fix the migration (or resolve the DB issue) and redeploy. Never edit an
  applied migration; never run `prisma migrate reset` in production.
- **Bad env change:** env edits trigger a new deploy; re-edit and redeploy to revert.
  A config-error deploy refuses to boot, so the running version is never replaced by
  an unsafe one.
- **Redis/DB incidents:** Key Value and PostgreSQL are stateful; Render restores them
  from snapshots, not deploys. See `docs/BACKUP_AND_RECOVERY.md`.
- After any rollback, spot-check `GET /api/v1/health/database`, `GET /api/v1/health/redis`
  and the latest `AuditLog` entries before resuming payout operations.

## 9. Post-deploy checklist

- [ ] All 10 services green; API `healthCheckPath` passing.
- [ ] `/api/v1/health/database` and `/api/v1/health/redis` both 200.
- [ ] `CORS_ORIGINS` contains the exact production frontend origin(s) — browser login
      works and cookies are accepted.
- [ ] At least one payment provider key set (`PROVIDER_MODE=live`).
- [ ] `WITHDRAWAL_DUAL_APPROVAL_MODE=ALL` (or `THRESHOLD` with a positive threshold).
- [ ] `ADMIN_EMAILS` set on the worker + weekly-reports + reconciliation-digest crons.
- [ ] Every payout administrator enrolled in fresh MFA (`POST /api/v1/mfa/enroll`).
- [ ] Migration status clean: `npx prisma migrate deploy` in `backend/` is a no-op.
