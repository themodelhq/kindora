# KINDORA v1.0.4 — Netlify Deployment Guide

Source of truth: `frontend/netlify.toml`. The frontend is a React 18 + Vite PWA
(`vite-plugin-pwa`) served by Netlify; the API runs on Render (see
`docs/RENDER_DEPLOYMENT_GUIDE.md`).

## 1. Connect the repo

1. Netlify dashboard → **Add new site → Import an existing project** → select the repo.
2. Set the **Base directory** to `frontend` (the config file lives at
   `frontend/netlify.toml`; Netlify picks it up automatically when base is set).
3. Everything below is already defined in `frontend/netlify.toml` — verify, don't
   retype:

| Setting | Value |
| --- | --- |
| Build command | `npm ci && npm run build` (runs `tsc --noEmit && vite build`) |
| Publish directory | `dist` |
| Node version | `22` (`[build.environment] NODE_VERSION`) |

## 2. Environment variables

Set in **Site settings → Environment variables** (or the deploy-time UI):

| Variable | Required | Purpose |
| --- | --- | --- |
| `VITE_API_URL` | Yes for production | Exact API origin, e.g. `https://api.kindora.com`. Consumed by `frontend/src/lib/http.ts` (`import.meta.env.VITE_API_URL ?? 'http://localhost:10000'`). No trailing slash. |
| `VITE_DEMO_MODE` | **Never in production** | See section 6. |

`VITE_*` variables are baked into the bundle at **build time**. Changing one requires a
new deploy (a re-publish alone is not enough). Do not put secrets in `VITE_*` vars —
everything here ships to the browser.

## 3. SPA redirects

`netlify.toml` defines a catch-all rewrite:

```toml
[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200
```

Every route serves the app shell, so deep links from WhatsApp, Facebook, Google, and
browser refreshes on client-side routes (e.g. `/dashboard/donations`,
`/campaigns/<slug>`) resolve correctly instead of 404ing.

## 4. Security headers (already configured)

The `[[headers]]` block applies to `/*`:

- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `X-Frame-Options: DENY`, `frame-ancestors 'none'` in CSP
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`
- CSP with `connect-src` allow-list: `'self' https://api.kindora.com https://*.onrender.com`
  plus the payment provider SDK origins (`*.paystack.co`, `api.flutterwave.com`,
  `api.stripe.com`, `api-m.paypal.com` / sandbox) and `*.sentry.io`.
- `Strict-Transport-Security: max-age=31536000; includeSubDomains`

Notes:
- `connect-src` includes `https://*.onrender.com` so a pre-DNS deployment (frontend on
  `*.netlify.app`, API on `*.onrender.com`) works without a code change. After DNS
  cutover, tighten CSP to the exact API origin.
- `frame-src` allows the Paystack/Flutterwave/Stripe/PayPal checkout frames only.

Caching rules: `/sw.js`, `/manifest.webmanifest`, `/index.html` are
`max-age=0, must-revalidate` (always fresh); `/assets/*` are immutable (hashed
filenames); `/icons/*` cache 7 days. The API responses are never cached here and the
service worker is NetworkOnly for `/api/` (see `frontend/vite.config.ts`), so
security-critical API updates always reach users — a stale service worker cannot pin
old behaviour.

## 5. PWA notes

- Service worker and web app manifest are generated by `vite-plugin-pwa`; icons ship in
  `frontend/public/icons/` (192, 512, maskable).
- `sw.js` is `must-revalidate` so pushes of a new deploy replace the worker promptly.
- Because `/api/` traffic bypasses the SW cache, MFA challenges (`POST /api/v1/mfa/challenge`)
  and payout actions always hit the live API — required, since MFA challenges are
  single-use and expire in 120 seconds.
- Verify after deploy: DevTools → Application → Manifest + Service Worker both load; no
  console errors from the CSP.

## 6. Demo-mode builds must never go to production

`VITE_DEMO_MODE` is baked in at **build time** and switches the entire API layer to the
offline demo adapter (`frontend/src/lib/demo/adapter.ts`) — fake campaigns, fake
donations, no backend calls. Its only purpose is PR previews and browser-based e2e
(`frontend/tests/e2e/demo*.spec.ts`, Playwright sets `VITE_DEMO_MODE: '1'`).

Rules:
- Never set `VITE_DEMO_MODE` in the production site's environment variables.
- Use a separate Netlify site (or deploy previews) for demo/e2e builds built with
  `VITE_DEMO_MODE=1 npm run build`.
- A production deploy showing demo data is a severity-1 incident: delete the deploy,
  remove the variable, redeploy, and confirm `VITE_API_URL` is set.

## 7. CORS on the Render side (mandatory pairing step)

The API validates browser origins from `CORS_ORIGINS` and cookie CSRF checks **fail
closed when it is empty**. After your Netlify domain exists (including deploy-preview
domains if you use them for admin work):

1. Render dashboard → `kindora-api` → Environment → `CORS_ORIGINS`.
2. Add the exact origin(s), e.g. `https://kindora.netlify.app,https://app.kindora.com`.
3. Save (this triggers an API redeploy) and re-test login from the browser.

Also set the API's `FRONTEND_URL` to the same production origin (used for email links),
and update the CSP `connect-src` in `frontend/netlify.toml` if the API origin is not
`api.kindora.com` or `*.onrender.com`.

## 8. Verify the deploy

```bash
SITE=https://<your-site>.netlify.app

# 1. SPA fallback for a client-side route
curl -sS -o /dev/null -w "%{http_code}\n" $SITE/dashboard/overview   # 200

# 2. Security headers present
curl -sSI $SITE | grep -iE "content-security-policy|strict-transport|frame-options"

# 3. Service worker is fresh
curl -sSI $SITE/sw.js | grep -i cache-control   # max-age=0, must-revalidate

# 4. API reachability from the bundle origin
curl -sS $VITE_API_URL_VALUE/api/v1/health
```

Then in a browser: log in, confirm no CORS errors, and confirm the service worker
registers. Run through one read-only admin page (e.g. `/admin/withdrawals`) before
allowing payout operations.
