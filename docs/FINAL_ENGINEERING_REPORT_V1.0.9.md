## D. Financial safety verification (spec §18.D)

1. **Can an ambiguous provider lookup cause another transfer? NO.** Every lookup returns an explicit outcome; only the strict documented per-provider not-found shape yields NOT_FOUND (`payout-approval-cycle`… adapters §2.2 predicates). AMBIGUOUS/ERROR release the claim with backoff, persist the outcome, and return `LOOKUP_BLOCKED` without calling `initiateTransfer` (unit: 4 tests; the adapters themselves classify, never throw).
2. **Can manual settlement race with a provider submission? NO.** The submission claims `PROVIDER_SUBMISSION_ACTIVE` inside the transaction holding the withdrawal row lock; `settleManual` rechecks unresolved attempts + pending outbox events under the SAME lock and claims `MANUAL_SETTLEMENT_ACTIVE` with an atomic upsert that only succeeds on IDLE/expired-lease rows; SETTLED is terminal. Proven by the real-PG concurrency test (§3.2/§12.5): exactly one path wins, ≤1 ledger posting.
3. **Can the requester approve their own withdrawal? NO.** Unchanged v1.0.4+ separation: requester can never be first/second approver (enforced at approval AND revalidated in every payout authorization); e2e `cannot approve`/`cannot settle` tests still pass.
4. **Can the same administrator occupy multiple approval/execution roles? NO.** The complete six-collision matrix is enforced by the centralized validator at initiation, submission (persisted `initiatedById` + `requireExecutor`), reconciliation (same) and manual settlement (intent authorization + settlement, both with the acting executor); unit tests cover every collision, missing and changed executor.
5. **Can a withdrawal without an approval snapshot be manually settled? NO.** `settleManual` requires the channel-bound manual snapshot (recomputed + constant-time compared); missing hashes ⇒ blocked; the two-step `authorizeManualIntent` binds it; legacy withdrawals are never grandfathered (§5.2) — e2e §4.5 updated expectations prove the refusal.
6. **Can Stripe payouts accidentally use the Paystack adapter? NO.** Stripe/PayPal are registry rejectors; `IMPLEMENTED` cannot include them; config validation rejects non-implemented providers; the Stripe donation path is untouched. (v1.0.7 closed the v1.0.6 defect; v1.0.9 re-audited and preserved.)
7. **Can duplicate reconciliation post the ledger twice? NO.** The reconciliation transaction locks withdrawal+attempt rows, uses conditional transitions, and posts through the unique `withdrawal:<id>` ledger reference; a replay re-derives MATCHED with `applied=false`; e2e §10 asserts exactly 1 ledger row after a replay.
8. **Can an expired worker lease trigger a second transfer without reconciliation? NO.** Lease reclaim only re-arms the submission AFTER the provider lookup returns an authoritative NOT_FOUND for the same reference; a FOUND lookup adopts the existing transfer; AMBIGUOUS/ERROR keep the reservation and retry the LOOKUP. Both e2e §12.3 scenarios prove the adopted/never-resubmitted and reclaimed-submitted-exactly-once paths.

## Supporting detail (implementation map)

- **Lookup outcome contract:** `backend/src/payouts/payout-provider.adapter.ts` — `PayoutLookupOutcome`, `PayoutLookupResult`, `classifyLookupHttpFailure` (401/403→ERROR, 429/5xx→AMBIGUOUS, 404→NOT_FOUND only via strict predicate, other→ERROR), `classifyLookupTransportFailure` (always AMBIGUOUS), `safeEqualHex` (constant-time).
- **Adapters:** Paystack — not-found predicate `404 + {status:false, message:"Transfer not found"} + data absent`; Flutterwave — authoritative empty reference-filtered list (`{status:"success", data:[]}` or `{content:[]}`); missing transfer fields on a success envelope classify AMBIGUOUS on both.
- **Coordination:** `PayoutSettlementGuard` (unique per withdrawal) — claim conditions are atomic conditional upserts; submission claims require IDLE or an EXPIRED provider lease; manual claims require IDLE or an EXPIRED provider lease (after the in-lock unresolved recheck); SETTLED never reclaimable.
- **Snapshots:** `PayoutApprovalCycleService.buildManualSnapshot/manualSettlementSnapshotHash` — canonical order-fixed SHA-256 over the sixteen binding fields; validated with `safeEqualHex`.
- **Migration 0006** is forward-only and additive: guard table (+backfill), lookup-outcome columns, two indexes, and the partial UNIQUE index. No historical migration was modified.
